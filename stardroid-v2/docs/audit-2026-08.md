# Static Analysis & Architectural Audit — Sky Map v2

**Scope:** `stardroid-v2/` (320 Kotlin files, ~51k LOC across `core:math`, `core:astronomy`,
`core:catalog`, `core:events`, `render:api`, `render:gles1`, `data`, `data:generator`, `app`).
`stardroid-v1/` was scanned at the manifest/secrets level only — AGENTS.md designates it
maintenance-only, and it is not the risk surface.

**Method:** manual read of every non-test source file in `core`, `data`, `render`, and the
high-traffic half of `app`, plus targeted greps for hazard patterns (non-null assertions, broad
catches, `runBlocking`, `GlobalScope`, PendingIntent mutability, duplicated constants, tracked
secrets).

**No code was modified when this was written.** Every finding below was a proposal.

**Status.** Every [HIGH], [MEDIUM] and [INFO] finding has been fixed in follow-up changes and is
marked *fixed* below. The [LOW] section (L1–L13) is still open. (I6 and I7 need no code fix —
I6's mitigation is external to this repo, and I7 is a list of positives, not a finding.)

---

## Headline

This is a well-engineered codebase. The things that usually generate audit findings are already
handled: FTS input is tokenized before it reaches SQLite, every `PendingIntent` is `IMMUTABLE`,
no secrets are tracked in git, `catch` blocks are narrow and each one carries a justification,
`!!` appears exactly twice in the entire non-test tree, and the pure/Android module boundary is
enforced by a Konsist gate. The design-decision log (D1–D93) is genuinely load-bearing — most
"suspicious" code turns out to have a documented reason.

What the audit did surface clusters into three themes: **one release-hygiene hole in the
manifest**, **a family of redundant ephemeris recomputations** in hot loops, and **per-frame
allocation churn in the label render path**. Nothing here is a data-loss or
remote-code-execution class defect.

## [HIGH]

### H1 — The renderer dev harness ships exported in release builds *(fixed)*

**File:** `app/src/main/AndroidManifest.xml:44-47`
(activity: `app/src/main/kotlin/com/google/android/stardroid/testscene/RendererTestActivity.kt:110`)

```xml
<!-- Dev harness and D19 perf-gate host; launchable via adb, no launcher entry. -->
<activity
    android:name=".testscene.RendererTestActivity"
    android:exported="true"
    android:label="Sky Map v2 (renderer test)" />
```

`RendererTestActivity` lives in `src/main`, not `src/debug`, and there is no debug-only manifest
(`app/src/*/AndroidManifest.xml` yields only `main`). It therefore ships in every release APK and
AAB, exported with no permission guard.

**Impact/Risk.** Any app on the device can `startActivity` it. It opens a GL surface, registers
sensor listeners, opens the Room catalog database (`SkyMapDatabaseFactory.createWithRecovery`,
line 334), and requests location. Concretely: an unprivileged third-party app can launch a
full-screen Sky Map activity over the user's current task (tapjacking / UI-confusion surface) and
can drive the app into work it would not otherwise do. It is also plain release bloat — the whole
`testscene` package and its test-scene assets are retained in the shipped binary.

The comment "launchable via adb" is the giveaway: `adb shell am start` on a *debug* build needs
no `exported="true"` for a same-package component only when the caller is the shell, and the
instrumentation test (`RendererPerfTest.kt:59`) uses `ActivityScenario`, which does not require
export either.

**Remediation.** Move the activity to a debug-only source set and manifest.

```
app/src/debug/AndroidManifest.xml     # <activity android:name=".testscene.RendererTestActivity" android:exported="true"/>
app/src/debug/kotlin/.../testscene/   # move RendererTestActivity.kt + TestScene.kt here
```

If the D19 perf gate must run against a release-ish build, keep it in `main` but set
`android:exported="false"` — `ActivityScenario` and same-UID `am start` both still work. Either
fix is a few lines; the source-set move is the better one.

## [MEDIUM]

### M1 — Sun and heliocentric positions are recomputed per body, per sample, in three hot loops *(fixed)*

**Files:**
- `app/src/main/kotlin/com/google/android/stardroid/layers/SolarSystemLayer.kt:137-197, 239-249`
- `core/astronomy/src/main/kotlin/com/google/android/stardroid/astronomy/SatellitePass.kt:167-216`
- `core/events/src/main/kotlin/com/google/android/stardroid/events/TonightSky.kt:281-324`

Three independent sites recompute a time-only quantity inside a per-object loop.

`SolarSystemLayer.buildScene` runs, for each of ten bodies: `earthDistanceAu`, `topocentricPosition`,
`magnitude`, `illuminatedFraction`, and `geocentricPosition(SUN)` — via `terminatorFor`, line 244.
Each of the first four resolves back through `KeplerianEphemeris.heliocentricPair`, which solves
Kepler's equation for the body *and* for Earth every single time. The Sun's geocentric position is
identical for all ten bodies at a given instant and is computed ten times; under `MeeusEphemeris`
that is ten runs of the full ch. 25 series plus ten precession-matrix builds.

`PassSearch.describePass` (line 188-194) calls `SatelliteMagnitude.sunDirectionTeme(time)` **and**
`MeeusEphemeris.topocentricPosition(SUN, ...)` at every 5-second sample of a pass — ~120 samples
for a 10-minute pass, each running the Meeus solar series and a precession rotation. The Sun moves
0.04° over the whole pass.

`TonightSky.planetEvents` (line 294-298) samples the Sun's altitude every 30 minutes *inside* the
per-planet loop, so the same 16 sun positions are computed once per candidate planet.

**Impact/Risk.** Not a correctness bug, and invisible in the once-a-minute steady state. It bites
in exactly the paths users notice: time travel drives `SolarSystemLayer` at tick rate; the tonight
widget and the digest notification run `planetEvents` and `tonightSatellitePasses` on a background
worker with a battery budget; and `TonightPasses.tonightSatellitePasses` fans `PassSearch` across
every tracked satellite. Rough order: 5–10× more floating-point work than the algorithms require.

**Remediation.** Hoist, don't cache-globally.

```kotlin
// SolarSystemLayer.buildScene — compute once, thread it through.
val sunPosition = ephemeris.geocentricPosition(SolarSystemBody.SUN, time)
for (body in byDistance) {
    ...
    terminator = terminatorFor(body, time, sunPosition)
}
```

```kotlin
// PassSearch.describePass — the Sun is effectively fixed across one pass.
val sunDirection = SatelliteMagnitude.sunDirectionTeme(start)
val skyIsDark = altitudeDeg(
    MeeusEphemeris.topocentricPosition(SolarSystemBody.SUN, start, observer), start, observer,
) <= CIVIL_TWILIGHT_SUN_ALT_DEG
// …then reuse both inside the sample loop.
```

```kotlin
// TonightSky.planetEvents — build the dark-sky sample list once, outside the mapNotNull.
val darkSamples = generateSequence(maxOf(now, eveningStart)) { it + 30.minutes }
    .takeWhile { it <= maxOf(now, eveningStart) + 8.hours }
    .filter { altitudeDeg(ephemeris.geocentricPosition(SUN, it), it, location) <= CIVIL_TWILIGHT_SUN_ALT_DEG }
    .toList()
```

A companion fix worth doing at the same time: memoize `Precession.dateFromJ2000` on its
`Instant` (`Precession.kt:42`). Every `precessedToJ2000`/`precessedFromJ2000` call currently builds
the full matrix — six trig calls plus three cubic polynomials — for one vector.

### M2 — The label render path allocates four objects per label, per frame *(fixed)*

**Files:**
- `render/gles1/src/main/kotlin/com/google/android/stardroid/render/gles1/LabelDrawer.kt:302-345`
- `render/gles1/src/main/kotlin/com/google/android/stardroid/render/gles1/LabelDeclutterer.kt:80-101`

`LabelDrawer.draw` builds an `ArrayList<Survivor>` and a `Survivor` data-class instance per
surviving label, then `survivors.map { … }` allocates a *second* full list of `Candidate` objects.
`LabelDeclutterer.declutter` then allocates a `BooleanArray`, a boxed `List<Int>` from
`candidates.indices.sortedByDescending { }`, a `mutableListOf<Rect>()`, and a `Rect` per candidate.
All of it is per-frame, at up to 60 fps.

The declutter itself is O(n²) against the kept set — acceptable at tens of labels, which is what
the existing `TODO(catalog slices)` at `LabelDrawer.kt:379` anticipates outgrowing.

**Impact/Risk.** GC pressure inside the draw loop, which on Android shows up as frame-time spikes
rather than a lower average — exactly the artifact the D19 perf gate is meant to catch, and exactly
what a fling or slew makes visible. The rest of this renderer is scrupulous about this (see the
`pointKey` and `drawOrder` caching comments in `GLSkyRenderer`); the label path is the one place the
discipline lapses.

**Remediation.** Replace the intermediate object lists with reusable parallel primitive arrays held
as GL-thread-only fields on `LabelDrawer`, grown only when the glyph count grows:

```kotlin
// GL-thread-only scratch, reused across frames.
private var survivorIndex = IntArray(0)
private var survivorX = FloatArray(0)
private var survivorY = FloatArray(0)
private var keptRects = FloatArray(0)   // 4 floats per kept rect
```

and change `LabelDeclutterer.declutter` to take those arrays plus a count, sorting an `IntArray`
of indices in place rather than via `sortedByDescending`. This also removes the boxing.

### M3 — The catalog search query is unbounded and undebounced *(fixed)*

**Files:**
- `data/src/main/kotlin/com/google/android/stardroid/data/CatalogDao.kt:85-101`
- `app/src/main/kotlin/com/google/android/stardroid/ui/search/SearchViewModel.kt:93-101`

`searchNameRows` has no `LIMIT`. A one-character query becomes the FTS prefix `a*`, which matches a
large fraction of every name row in the catalog across the whole locale chain; all of them are
materialized into `List<SearchNameRow>`, grouped, and sorted in Kotlin
(`RoomCatalogRepository.searchByPrefix:111-131`) before `.take(limit)` throws almost all of them
away.

`SearchViewModel.suggestions` maps `_query` through `mapLatest` with **no `debounce`**. `mapLatest`
cancels the *coroutine* on the next keystroke, but a Room suspend query is not cancellable mid-flight
— the query runs to completion on the query executor regardless.

**Impact/Risk.** Typing "andromeda" fires nine full-catalog scans, the first of which is the
worst. On a low-end device this is the visible stutter in the search sheet.

**Remediation.** Both halves.

```kotlin
// CatalogDao — bound the candidate set in SQL. Over-fetch relative to the display limit so
// Kotlin-side ranking still has something to rank.
        WHERE n.locale IN (:locales)
          AND n.id IN (SELECT docid FROM object_name_fts WHERE object_name_fts MATCH :ftsQuery)
        ORDER BY o.magnitude IS NULL, o.magnitude
        LIMIT :candidateLimit
```

```kotlin
// SearchViewModel — one query per pause, not per keystroke.
@OptIn(FlowPreview::class, ExperimentalCoroutinesApi::class)
val suggestions: StateFlow<List<SearchHit>> =
    _query
        .debounce(SEARCH_DEBOUNCE_MILLIS)   // 150L
        .mapLatest { … }
```

### M4 — `runBlocking` on the main thread inside a `BroadcastReceiver` *(fixed)*

**File:** `app/src/main/kotlin/com/google/android/stardroid/satellites/PassAlerts.kt:153`

```kotlin
override fun onReceive(context: Context, intent: Intent) {
    ...
    // A BroadcastReceiver's process can be killed the moment onReceive returns, so this small
    // preference read is done inline rather than handed to a coroutine that may never run.
    val stillWanted = runBlocking { passAlertsEnabled(context) }
```

The reasoning in the comment is right — the work *must* finish before `onReceive` returns — but
`runBlocking` is the wrong instrument. `onReceive` runs on the main thread, and
`passAlertsEnabled` reads DataStore, which on a cold process means opening and parsing the
preferences file from disk. The receiver's ANR budget is 10 seconds, and this fires from an
`AlarmManager` wake-up in Doze, which is the worst possible moment for disk latency.

**Impact/Risk.** An ANR on the pass-alert path, on a wake-from-Doze, on a device under I/O
contention. Low probability per firing, but it is a main-thread disk read with no ceiling.

**Remediation.** `goAsync()` is the API built for exactly this — it keeps the process alive past
`onReceive` and gives you a wall-clock budget without blocking the main thread.

```kotlin
override fun onReceive(context: Context, intent: Intent) {
    val start = PassAlerts.startTimeFrom(intent) ?: return
    val noradId = PassAlerts.noradIdFrom(intent)
    val pending = goAsync()
    CoroutineScope(SupervisorJob() + Dispatchers.IO).launch {
        try {
            if (passAlertsEnabled(context)) SatellitePassNotifier.post(context, noradId, start)
        } finally {
            pending.finish()
        }
    }
}
```

### M5 — Share compositing holds four full-screen ARGB_8888 bitmaps with no `recycle()` *(fixed)*

**File:** `app/src/main/kotlin/com/google/android/stardroid/share/SkyShare.kt:61-74, 162-204, 241-300`
(and `app/src/main/kotlin/com/google/android/stardroid/camera/SkyCameraPreview.kt:127-147`)

`arShareLayouts` builds **both** layouts eagerly so the sheet can preview them. On a 1440×3120
display that is:

| Bitmap | Approx. bytes |
|---|---|
| `map` (from `captureMap`) | 18 MB |
| `cameraStill` (full-res, plus an un-recycled pre-rotation copy) | 2 × ~12 MB |
| `overlayComposite` result | 18 MB |
| `sideBySideComposite` result (double width) | 36 MB |
| two `appendFooter` results | 18 + 37 MB |
| `mapOverBlack` intermediates (×2) | 36 MB |

Nothing is `recycle()`d, so all of it is live simultaneously until GC. `SkyCameraPreview.takeStill`
(line 135-143) additionally leaks `decoded` when it rotates the still into a new bitmap.

**Impact/Risk.** ~170 MB of transient bitmap allocation on a high-DPI device. This is a plausible
`OutOfMemoryError` on the "share what I'm seeing" path — which is the app's growth loop, so a crash
here is expensive out of proportion to its frequency.

**Remediation.** Recycle every intermediate as soon as it is consumed, and build the two AR layouts
lazily (the sheet shows one at a time).

```kotlin
private fun mapOverBlack(map: Bitmap): Bitmap { … }   // caller recycles `map` if it owns it

private fun appendFooter(content: Bitmap, branding: Branding): Bitmap {
    val result = …
    canvas.drawBitmap(content, 0f, 0f, null)
    content.recycle()          // content is always a private intermediate
    …
}
```

and in `takeStill`:

```kotlin
} else {
    Bitmap.createBitmap(decoded, 0, 0, decoded.width, decoded.height, matrix, true)
        .also { decoded.recycle() }
}
```

Consider also downsampling the capture to a share-appropriate long edge (2048 px is generous) before
compositing — the share target re-encodes it anyway.

### M6 — The CelesTrak response body is read without a size cap *(fixed)*

**File:** `data/src/main/kotlin/com/google/android/stardroid/data/satellites/CelesTrakClient.kt:92`

```kotlin
HttpURLConnection.HTTP_OK ->
    FetchOutcome.Success(
        body = connection.inputStream.bufferedReader().use { it.readText() },
```

The expected payload is ~1 KB. `readText()` will happily materialize whatever arrives. The
`fetchAndStore` guard downstream (`SatelliteElementsRepository.kt:176`) catches a captive-portal
login page *after* it has already been read into memory, and `Tle.parseCatalog` then splits it into
a full line list on top of that.

**Impact/Risk.** A captive portal, a hijacked DNS answer, or a CelesTrak misconfiguration returning
a large body turns a 1 KB background fetch into an OOM in a WorkManager job. Low likelihood, trivial
to close.

**Remediation.** Cap the read, and treat an over-long body as an unusable one.

```kotlin
private const val MAX_BODY_BYTES = 2 * 1024 * 1024   // ~2000× the expected payload

HttpURLConnection.HTTP_OK -> {
    val text = connection.inputStream.bufferedReader().use { reader ->
        val buffer = CharArray(MAX_BODY_BYTES)
        val read = reader.read(buffer, 0, MAX_BODY_BYTES)
        if (read < 0) "" else String(buffer, 0, read)
    }
    if (connection.inputStream.read() >= 0) {
        FetchOutcome.UnusableBody("body exceeds $MAX_BODY_BYTES bytes")
    } else {
        FetchOutcome.Success(body = text, lastModified = connection.getHeaderField("Last-Modified"))
    }
}
```

### M7 — Pass alerts are silently lost across a reboot *(fixed)*

**Files:** `app/src/main/kotlin/com/google/android/stardroid/satellites/PassAlerts.kt:78-98`,
`app/src/main/AndroidManifest.xml`

`AlarmManager` alarms do not survive a device reboot, and the manifest declares no
`BOOT_COMPLETED` receiver. A user who arms tonight's ISS alert and reboots — or whose phone reboots
for a system update overnight — gets nothing, with no signal that anything was dropped.

**Impact/Risk.** Silent feature failure on the one notification the design document calls
"the single most important implementation note in the feature." The failure is invisible: the user
concludes the alert doesn't work.

**Remediation.** Add a boot receiver that re-derives and re-arms.

```xml
<uses-permission android:name="android.permission.RECEIVE_BOOT_COMPLETED" />
...
<receiver android:name=".satellites.PassAlertBootReceiver" android:exported="false">
    <intent-filter><action android:name="android.intent.action.BOOT_COMPLETED" /></intent-filter>
</receiver>
```

The receiver can simply enqueue the existing work that computes tonight's passes and calls
`PassAlerts.armBestPass` — no new logic, just a new trigger.

### M8 — `SatelliteElementsRepository.current()` re-reads and re-parses the whole TLE file for a single enum *(fixed)*

**Files:**
- `app/src/main/kotlin/com/google/android/stardroid/satellites/SatelliteElementsFlow.kt:73-78`
- `data/src/main/kotlin/com/google/android/stardroid/data/satellites/SatelliteElementsRepository.kt:76-89`
- `app/src/main/kotlin/com/google/android/stardroid/satellites/TonightPasses.kt:55-56, 105-106, 134-135`

`current()` does `readText()` + `Tle.parseCatalog()` over the entire file. `satelliteUiStatusFlow`
calls it purely to read `.freshness` and discards the parsed list. `TonightPasses` calls it inside
`withContext(Dispatchers.Default)` — a compute dispatcher — for what is blocking disk I/O.

**Impact/Risk.** Wasted parse on a 5-minute poll (small), and blocking I/O on a `Default` worker
that is sized to CPU count (worse — it can starve the compute pool while the pass search runs).

**Remediation.** Add a cheap freshness-only query and fix the dispatcher.

```kotlin
/** Freshness without parsing the element sets — what the Layers sheet actually needs. */
fun freshness(): ElementFreshness {
    val writtenAt = store.elementsWrittenAt() ?: return ElementFreshness.ABSENT
    return freshnessFor((clock.now() - writtenAt).inWholeSeconds / SECONDS_PER_DAY)
}
```

and in `TonightPasses`, split the phases: `withContext(Dispatchers.IO) { repository.current() }`
for the read, `withContext(Dispatchers.Default) { … }` for the pass search.

## [LOW]

### L1 — `catch (e: Exception)` around `repeatOnLifecycle` swallows cancellation

**File:** `app/src/main/kotlin/com/google/android/stardroid/ui/MainActivity.kt:421-434`

```kotlin
lifecycleScope.launch {
    try {
        val layers = catalogAccess.layerRegistry().layers
        repeatOnLifecycle(Lifecycle.State.STARTED) { … }
    } catch (e: Exception) {
        // TODO: Handle database/registry load failure gracefully per D24
    }
}
```

`CancellationException` is an `Exception`, so every normal teardown of this coroutine is caught and
discarded here. It happens to be harmless — the scope is already cancelling — but it breaks
structured concurrency's contract, and any future `finally`/cleanup added inside will behave
unexpectedly. Separately, a genuine database failure produces an app that renders an empty sky with
no log line and no user-visible message.

**Remediation.**

```kotlin
} catch (e: CancellationException) {
    throw e
} catch (e: Exception) {
    Log.e(TAG, "Layer registry failed to load; the map will be empty", e)
    // TODO(D24): surface this to the user.
}
```

### L2 — `floorMod` can return `n` for tiny negative inputs

**File:** `core/math/src/main/kotlin/com/google/android/stardroid/math/Angles.kt:21-27`

```kotlin
fun floorMod(a: Double, n: Double): Double {
    val r = a % n
    return if (r < 0) r + n else r
}
```

For `a = -1e-18, n = 360.0`, `r + n` rounds to exactly `360.0` — outside the documented `[0, n)`.
The same holds for `normalizeRadians` returning `2π`. `RaDec.fromGeocentricVector` and
`meanSiderealTimeDeg` both funnel through this.

**Impact/Risk.** No current caller indexes an array by the result, so nothing breaks today. It
becomes a real out-of-bounds the moment someone writes `(normalizeDegrees(x) / 360.0 * N).toInt()`.

**Remediation.**

```kotlin
fun floorMod(a: Double, n: Double): Double {
    val r = a % n
    if (r >= 0) return r
    val shifted = r + n
    return if (shifted < n) shifted else 0.0
}
```

### L3 — `azimuthDeg` divides by `cos(altitude)` and `cos(latitude)`

**File:** `core/astronomy/src/main/kotlin/com/google/android/stardroid/astronomy/RiseSet.kt:166-180`

```kotlin
val sinAz = -sin(haRad) * cos(decRad) / cos(altRad)
val cosAz = (sin(decRad) - sinAlt * sin(latRad)) / (cos(altRad) * cos(latRad))
```

At the zenith (`altRad = ±π/2`) and at a geographic pole (`latRad = ±π/2`) these divisors vanish,
producing `±Infinity` and an `atan2` of two infinities — a meaningless-but-finite azimuth, or
`NaN`. `SkyModel.localFrame` clamps latitude to ±89° for exactly this reason (line 96-97); this
function does not.

**Remediation.** Return a documented sentinel rather than arithmetic noise.

```kotlin
val cosAlt = cos(altRad)
val cosLat = cos(latRad)
if (abs(cosAlt) < 1e-9 || abs(cosLat) < 1e-9) return 0.0   // azimuth undefined at zenith/pole
```

### L4 — `riseSetUtHours` discards a solution that converges on the final iteration

**File:** `core/astronomy/src/main/kotlin/com/google/android/stardroid/astronomy/RiseSet.kt:217`

```kotlin
return if (iterations == MAX_ITERATIONS) null else ut
```

If the loop's 25th pass brings `|delta|` under tolerance, the loop exits *and* `iterations == 25`,
so a converged answer is thrown away. The conservative direction, but wrong — the caller then
retries the whole day offset.

**Remediation.** Track convergence explicitly rather than inferring it from the counter:
`return if (abs(delta) > CONVERGENCE_HOURS) null else ut`.

### L5 — `PassSearch.allPasses` reports a truncated *start* while refusing a truncated *end*

**File:** `core/astronomy/src/main/kotlin/com/google/android/stardroid/astronomy/SatellitePass.kt:115, 134-136`

```kotlin
var passStart: Instant? = if (previousAltitude > minimumElevationDeg) from else null
...
// A pass still in progress when the window ends is deliberately dropped rather than
// reported with a truncated end time — a pass whose "sets at" is really "we stopped
// looking" would be a lie…
```

The comment states the principle clearly, and the code applies it to the window's *end* but not its
*start*: a satellite already above the horizon at `from` gets a pass whose `start` is "we started
looking", with a `startAzimuthDeg` measured at that arbitrary moment. That is the same lie, at the
other end.

**Remediation.** Either bisect backwards to find the true rise, or — matching the end-of-window
rule — drop the in-progress pass: `var passStart: Instant? = null`.

### L6 — `SatellitePassNotifier.post` lacks the guard its sibling documents as mandatory

**Files:** `app/src/main/kotlin/com/google/android/stardroid/satellites/SatellitePassNotifier.kt:85`
vs `app/src/main/kotlin/com/google/android/stardroid/notifications/SkyNotifier.kt:152-168`

`SkyNotifier.post` calls itself "the one guarded `notify` call" and wraps the call in both an
explicit `POST_NOTIFICATIONS` check and a `try/catch (SecurityException)` for the
revoked-between-check race. `SatellitePassNotifier.post` calls
`NotificationManagerCompat.notify` bare, relying only on `canPost`'s
`areNotificationsEnabled()`.

`areNotificationsEnabled()` does reflect the runtime permission on API 33+, so the common path is
covered — but the race `SkyNotifier` explicitly guards against is unguarded here, and this call
site runs inside a `BroadcastReceiver`, where an uncaught `SecurityException` is a crash.

**Remediation.** Route it through the guarded helper: make `SkyNotifier.post` internal-visible and
have `SatellitePassNotifier` call it, so there is one guarded `notify` in the codebase rather than
a documented one and an undocumented one.

### L7 — The δT polynomial is applied far outside its stated validity range

**File:** `core/astronomy/src/main/kotlin/com/google/android/stardroid/astronomy/Time.kt:42-46`

The KDoc scopes the Espenak–Meeus fit to 2005–2050; `KeplerianEphemeris.validRange` is 1800–2050
(`KeplerianEphemeris.kt:42-45`), and the time-travel feature lets the user drive the clock. The
quadratic is evaluated unconditionally, so a user travelling to 1850 gets a δT of roughly −25 s
against a true value near +7 s.

**Impact/Risk.** Sub-arcminute for everything but the Moon; a fraction of a Moon-width for the Moon
at the extremes. Not visible in normal use, and `validRange` already exists to express the bound —
it just isn't consulted here.

**Remediation.** Clamp the argument to the fitted window and note the residual in the KDoc:
`val u = (year - 2000.0).coerceIn(5.0, 50.0)`.

### L8 — Public `MutableSharedFlow` fields on `MapViewModel`

**File:** `app/src/main/kotlin/com/google/android/stardroid/ui/map/MapViewModel.kt:178, 437, 459`

```kotlin
val arPermissionDenials = MutableSharedFlow<Boolean>(extraBufferCapacity = 1)
val arAlignmentReceipts = MutableSharedFlow<Unit>(extraBufferCapacity = 1)
val labelSizeHints = MutableSharedFlow<Unit>(replay = 1, extraBufferCapacity = 1)
```

Every other observable on this class follows the private-backing-field convention
(`_camera`/`camera`, `_referenceFrame`/`referenceFrame`, …). These three are exposed mutable, so any
collaborator can emit into them. `arPermissionDenials` is *intentionally* written from the activity;

**Remediation.** Give the two internal ones the standard treatment
(`private val _labelSizeHints` + `val labelSizeHints: SharedFlow<Unit>`), and for
`arPermissionDenials` expose a `fun onCameraPermissionDenied(canAsk: Boolean)` so the write path is
named rather than implicit.

### L9 — `Tle.parseCatalog` leaks a stale title onto the next satellite

**File:** `core/astronomy/src/main/kotlin/com/google/android/stardroid/astronomy/Tle.kt:142-167`

`pendingName` is cleared only on the branch that consumes a complete two-line set. When a `"1 "`
line is followed by something that is not a `"2 "` line, the loop does `index++; continue` without
clearing `pendingName` — so the next well-formed set inherits the previous object's name.

**Impact/Risk.** A mislabelled satellite in the map layer and the info card after a malformed feed
segment. The feed is well-formed in practice; this is the defence-in-depth that the surrounding
"one bad line should cost one satellite" comment is aiming for.

**Remediation.** Clear it on both paths.

```kotlin
val second = lines.getOrNull(index + 1)
if (second == null || !second.startsWith("2 ")) {
    pendingName = ""
    index++
    continue
}
```

### L10 — Dead conditional in the render loop

**File:** `render/gles1/src/main/kotlin/com/google/android/stardroid/render/gles1/GLSkyRenderer.kt:268-270`

```kotlin
if (state.nightMode != pointKey.first || state.magnitudeLimit != pointKey.second) {
    pointKey = Pair(state.nightMode, state.magnitudeLimit)
}
```

The guard is equivalent to the unconditional assignment, minus the `Pair` allocation it was written
to avoid — which it does still avoid, so this is a *correct* optimization with a misleading shape.
Worth a one-line comment saying so, or the guard reads as a bug to the next reader.

### L11 — `Vector3.cosineSimilarity` returns `NaN` for a zero vector

**File:** `core/math/src/main/kotlin/com/google/android/stardroid/math/Vector3.kt:62-63`

Every other degenerate case in this file is guarded (`normalized()` returns `ZERO` below 1e-6,
`Matrix3.inverse` returns `null`). This one divides by zero and propagates `NaN` silently.
No current caller passes a zero vector; the inconsistency is the finding.

### L12 — `MIN_PHASE_FACTOR`'s comment describes the opposite geometry

**File:** `core/astronomy/src/main/kotlin/com/google/android/stardroid/astronomy/SatelliteMagnitude.kt:88-92, 127-128`

> "Floored so a satellite seen almost exactly against the Sun does not produce an infinite
> magnitude" … "Keeps a near-zero phase angle from driving the magnitude to negative infinity."

The floor applies at phase angle **180°** (`(1 + cos 180°)/2 = 0`), not near zero — at 0° the
factor is 1 and nothing is at risk. The code is right; both comments are inverted, on a file whose
whole KDoc is about not confusing directions.

### L13 — Inconsistent `@Throws` on `TleStore`

**File:** `data/src/main/kotlin/com/google/android/stardroid/data/satellites/TleStore.kt:65, 114`

`writeElements` carries `@Throws(IOException::class)` and documents it; `writeState` throws the same
exception from the same rename-failure path (line 129) with neither annotation nor KDoc. The caller
does wrap it (`SatelliteElementsRepository.kt:196`), so this is documentation drift rather than a
bug.

### I2 — Four different `EARTH_RADIUS`-family constants, two sharing a name *(fixed)*

| Constant | Value | File | Why |
|---|---|---|---|
| `EARTH_RADIUS_KM` | 6378.135 | `Sgp4.kt:384` | WGS-72, required by SGP4's own fit |
| `EARTH_RADIUS_KM` | 6371.0 | `SatelliteMagnitude.kt:119` | mean radius, shadow cylinder |

### I3 — Repeated locale-name-picking idiom across three `RoomCatalogRepository` methods *(fixed)*

`meteorShowers` (line 80-89), `galleryItems` (line 221-231), and `toCatalogObject` (line 257-265)
each write the same four-step incantation: filter non-null names → sort primary-first, then by name →

### I5 — No backup rules declared *(fixed)*

**File:** `app/src/main/AndroidManifest.xml`

`android:allowBackup` is unset, so it defaults to `true`, and no `android:dataExtractionRules` /

That is arguably the correct product behavior (a returning user wants their location back), and it

## Top 3 Recommended Actions

**1. Move `RendererTestActivity` into a debug source set. (H1)**
The only finding in this audit with a third-party attack surface, and the cheapest to fix — a file
move plus a four-line `src/debug/AndroidManifest.xml`. It also shrinks the release binary. Do this
before the next Play Store upload; the app is at `2.0.0-beta01` and this should not reach production.

**2. Hoist the redundant solar/heliocentric computations out of the three hot loops. (M1)**
Highest performance return per line changed anywhere in the codebase: three localized edits remove
roughly 5–10× of the floating-point work in `SolarSystemLayer.buildScene`,
`PassSearch.describePass`, and `TonightSky.planetEvents`. It directly improves time-travel
smoothness and background-worker battery cost, and it needs no architectural change — the values
being recomputed are already pure functions of the instant. Memoizing `Precession.dateFromJ2000`
alongside it is a further four lines.

**3. Bound and debounce catalog search, then fix the label-path allocations. (M3, M2)**
These are the two findings users can feel. M3 is a `LIMIT` in one SQL string plus one `.debounce()`
operator — an afternoon, with an immediate effect on search-sheet responsiveness on low-end devices.
M2 is a larger job (reusable scratch arrays in `LabelDrawer` and an index-array rewrite of
`LabelDeclutterer.declutter`) and should be sequenced against the existing
`TODO(catalog slices)` batching work at `LabelDrawer.kt:379` — the two touch the same code, and
doing them together avoids paying the review cost twice.

## Remediation log

**H1 — fixed.** `RendererTestActivity` and `TestScene` moved to `app/src/debug/kotlin/`, with the
activity declared in a new `app/src/debug/AndroidManifest.xml`. Verified: the merged `gmsRelease`
manifest no longer declares the activity and `gmsRelease` compiles no `testscene` classes, while
the debug variant keeps both and `adb shell am start -n
com.google.android.stardroid/.testscene.RendererTestActivity` still resumes it. `androidTest`
builds against the debug variant, so `RendererPerfTest` is unaffected.

**M1 — fixed, with one deliberate deviation.** `SolarSystemLayer.buildScene` computes the Sun's
geocentric position once and threads it into `terminatorFor`. `TonightSky.planetEvents` builds the
dark-sky sample list once outside the per-planet loop. `Precession` memoizes both rotations for the
last instant behind a volatile single-entry cache.

In `PassSearch.describePass` the proposed fix froze `skyIsDark` at the pass start. That would have
been wrong: the Sun's *altitude* changes at 15°/hour of Earth rotation, so over a 10-minute pass it
moves ~2.5° — enough to flip the civil-twilight test near dusk. What is actually hoisted is the
Sun's inertial direction and its equatorial coordinates (both time-only, and both what cost the
Meeus series and the precession build); `altitudeDeg` is still evaluated per sample from the frozen
coordinates, which is three trig calls and keeps the twilight boundary exact.

**M2 — fixed.** `LabelDeclutterer.Candidate`/`List<Candidate>` replaced by
`LabelDeclutterer.Candidates`, a growable struct-of-arrays that also carries the declutter scratch
(index order, kept rects) and the visibility output. `LabelDrawer` owns one instance as a
GL-thread-only field and refills it each frame, so the label path allocates nothing per frame. The
priority sort is a stable in-place insertion sort over an `IntArray`, which preserves the old
`sortedByDescending` tie-breaking and removes the boxing. The O(n²) overlap scan and the batching
`TODO` are unchanged.

**M3 — fixed.** `searchNameRows` gained a `LIMIT`, ordered by the head of the Kotlin ranking
(whole-name prefix, then primary name, then brightness) rather than by magnitude alone, so
truncation drops the rows the ranking would have dropped anyway; the prefix test uses `substr`
equality, not `LIKE`, so user text can't be read as a wildcard pattern. The candidate set
over-fetches at 20× the display limit. `SearchViewModel.suggestions` gained a 150 ms `debounce`,
skipped for a blank query so clearing the field blanks the list at once.

**I1 — fixed, primary case only.** The three copies of `DEFAULT_LOCATION` are gone;
`MapViewModel` and `RendererTestActivity` now import `LocationController.DEFAULT_LOCATION`. The
secondary suggestion in the same finding — naming the shared FOV value in `render:api` so
`SolarSystemLayer.CALIBRATION_FOV_DEG` and `MapViewModel.INITIAL_FOV_DEG` don't need a
drift-detecting test — was not done; both constants and the guarding test in
`SolarSystemLayerTest` are unchanged.

**I2 — fixed.** The two colliding `EARTH_RADIUS_KM` constants are renamed to
`SGP4_EARTH_RADIUS_KM` (`Sgp4.kt`) and `MEAN_EARTH_RADIUS_KM` (`SatelliteMagnitude.kt`); the two
already-distinct constants (`WGS84_EQUATORIAL_RADIUS_KM`, `EARTH_EQUATORIAL_RADIUS_KM`) were
untouched, as intended.

**I3 — fixed.** `RoomCatalogRepository` now has a `NameCandidate` interface implemented by the
three row types, with a shared `bestNameInChain` extension (built on the existing `pickByChain`)
replacing the three duplicated filter/sort/pick blocks in `meteorShowers`, `galleryItems`, and
`toCatalogObject`.

**I4 — fixed.** The dead `"′"`/`"″"` entries are removed from `MINUTE_UNITS`/`SECOND_UNITS` in
`CoordinateParser`; the normalization pass that folds both marks to `'`/`"` before tokenizing is
unchanged, so this is a no-op removal of unreachable entries.

**I5 — fixed.** `AndroidManifest.xml` now declares `android:dataExtractionRules` and
`android:fullBackupContent` explicitly (both pointing at rule sets that keep the existing
Android-default backup behavior — including the saved location — rather than narrowing it), and
`PRIVACY_POLICY.md` gained a "Backup" section stating that plainly. The decision is now explicit
rather than made by omission; the underlying product behavior is unchanged.

**M4 — fixed.** `PassAlertReceiver.onReceive` uses `goAsync()` and a background coroutine for the
opt-in re-check instead of `runBlocking`. The comment's reasoning was right — the check must
finish before `onReceive` returns — but `goAsync()` is the API that buys that without blocking the
main thread on a DataStore read during a Doze wake-up.

**M5 — fixed, with two deviations.** `SkyShare` now documents an explicit ownership rule (a
private intermediate is recycled by whoever consumes it; a bitmap passed in from outside is never
recycled there) and follows it, which closes the outright leaks — `mapOverBlack`'s result inside
`sideBySideComposite`, and `decoded` in `SkyCameraPreview.takeStill` when the still needs rotating.
`MapScreen` recycles the captures it owns, including on the still-failed path where the map bitmap
was previously leaked outright before falling back to `shareSky`'s own capture. The larger win is
that captures are downsampled to a 2048 px long edge before compositing, which scales every bitmap
in the pipeline down at once; the scale arithmetic is extracted as `shareScaledSize` next to
`centerCrop` so the resolution policy is unit-testable without Android.

The proposed remediation said to build the two AR layouts lazily, "the sheet shows one at a time".
It does not: `ShareLayoutSheet` renders both as thumbnails simultaneously, so lazy construction
would break the picker. Not done.

Relatedly, the two finished layouts are deliberately **not** recycled. They are held in Compose
state and drawn, so recycling them races with the recomposition that drops the sheet, and drawing
a recycled bitmap is a crash. Bounding them via the downsample — roughly 25 MB for the pair, and
ordinary garbage — gets the same result without introducing a use-after-recycle hazard.

Verified on device (Pixel_5 AVD, 1080×2340): the map-only share writes a 1035×2048 image plus
footer, the AR side-by-side writes 2078×2375, both fully rendered with intact footer branding, and
no recycled-bitmap or OOM entries in logcat.

**M6 — fixed.** `HttpUrlConnectionCelesTrakClient` reads the response body a chunk at a time into a
`StringBuilder` inside `use {}`, refusing as soon as the accumulated length would exceed a 2 MB
cap and reporting `FetchOutcome.UnusableBody`. Note the cap is deliberately *not* pre-allocated:
the first cut of this fix allocated a 2 MB `CharArray` per fetch, which made the normal ~1 KB case
dramatically worse. This also adds the first tests for the class, pinning the cap in both
directions.

**M7 — fixed.** A `PassAlertBootReceiver` on `BOOT_COMPLETED` (plus the `RECEIVE_BOOT_COMPLETED`
permission). It carries no logic of its own: `SkyMapApplication.onCreate` already re-derives and
re-arms the best pass on every process start, so the receiver only needs to exist for the boot
broadcast to bring the process up — which is exactly what the finding suggested.

**M8 — fixed.** `SatelliteElementsRepository.freshness()` reads only the small state file's
`elementsWrittenAt`, and `satelliteUiStatusFlow` uses it instead of `current()`, whose parsed
element list it discarded. `TonightPasses`'s three functions now split an IO-dispatched read from
the Default-dispatched compute, rather than doing blocking disk I/O on a CPU-sized dispatcher that
the pass search also runs on.
